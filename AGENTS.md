# Правила репозитория

## Назначение

- `pi-russian-style` — пакет Pi для естественного русского технического языка.
- Расширение добавляет компактный системный блок, команды управления, пассивную диагностику и явный stateful workflow Humanizer.
- Пассивная диагностика не меняет обычные ответы, не вызывает дополнительную модель и не блокирует TUI. Humanizer создаёт отдельный производный результат только по явной команде пользователя.

## Карта проекта

- `src/index.ts` — жизненный цикл расширения, команды и обработчики событий Pi.
- `src/prompt.ts` — системная инструкция и распознавание явного запроса на английский язык.
- `src/diagnostics.ts` — фильтр сообщений, признаки, решения и запуск `humanizer-ru`.
- `src/diagnostic-queue.ts` — ограниченная однопоточная очередь.
- `src/runtime-diagnostics.ts` — фоновая обработка, привязка entry ID и JSONL-хранилище.
- `src/humanizer.ts` — draft lifecycle, точные patch-операции, lint и публикация `/ru-clean`.
- `prompts/ru-clean.md` — редактируемый instruction resource команды `/ru-clean`, а не prompt template Pi.
- `skills/humanizer-ru/` — canonical skill, references и lint, поставляемые с пакетом.
- `eval/` — компактный обезличенный регрессионный корпус.
- `review/` и `docs/window-observation.md` — локальная разметка и методика работы с приватными диагностическими данными.
- `research/`, `docs/research/` и `docs/roadmap.md` — локальные исследовательские материалы; они намеренно исключены из public-версии правилами `.gitignore`.
- `benchmarks/` — измерение критического пути и фоновой диагностики.

## Инварианты

- Обработчик `message_end` должен возвращать управление до запуска линтера и файловой записи.
- Фоновая очередь ограничена, выполняет не более одной задачи одновременно и безопасно пропускает работу при перегрузке.
- На `session_shutdown` активная работа отменяется; старая сессия не должна уведомлять новую.
- Ошибка, тайм-аут или отсутствие lint не должны ломать обычный ответ или TUI.
- Диагностический JSONL не хранит исходный текст; допустимы хэш, длина, признаки и служебные идентификаторы.
- Каталог состояния создаётся с правами `0700`, файл — `0600`.
- `entry_id` проверяется по времени, провайдеру, модели и SHA-256 текста; при недоступном JSONL остаётся `null`.
- Уведомление допустимо только при сочетании сильных сигналов. Одиночная мелочь даёт не более `record`.
- Код, команды, пути, API, идентификаторы и точные внешние сообщения не считать лишним английским.
- `humanizer-ru` поддерживается в этом репозитории как canonical package content. Не создавать вторую вручную редактируемую копию.
- Humanizer не становится универсальным редактором кода: file/docstring/comment staging использует обычные `read`, `ast-index-nav` и `edit`.

## Изменения

- Делать минимальное полное изменение в ближайшем ответственном модуле.
- Для нового поведения добавлять тест отказа или граничного случая, а не только счастливого пути.
- Изменение схемы диагностической записи требует новой версии `schema` или доказанной обратной совместимости.
- Изменение правил диагностики требует обновить `DIAGNOSTIC_RULES_VERSION` и связанные тесты.
- Производительные изменения в `message_end` проверять на коротком и длинном ответах.
- Сырые сессионные данные, абсолютные пользовательские пути, Pi entry ID и содержимое `.runtime/` в Git не добавлять.
- Не перезаписывать несвязанные незакоммиченные изменения.
- Локальные корпуса, результаты разметки и исследовательские заметки не добавлять в Git даже в обезличенном виде без отдельного решения владельца.
- При изменении пользовательского поведения, tool-контракта, skill, команд или установки одновременно обновлять релевантные `README.md`, `AGENTS.md` и/или `docs/`; не оставлять документацию с обещаниями, которых runtime не выполняет.

## Проверка

- Основной полный цикл: `bash run-checks.sh`.
- После него выполнить `git diff --check`.
- При изменении загрузки расширения дополнительно проверить установленный Pi без модельного вызова: `timeout 20 pi --no-extensions -e "$PWD" --list-models >/dev/null`.

Полный цикл должен подтвердить TypeScript-тесты, строгую типизацию, Python-тесты, benchmark и текстовые инварианты.

Если проверка недоступна из-за внешней зависимости, явно назвать непроверенное и не подменять результат предположением.

## Коммиты

- Использовать Conventional Commits: `type(scope): summary`.
- Основные типы: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `perf`, `build`, `ci`, `revert`.
- Писать summary в повелительной форме, по-английски, без точки; пример: `feat(diagnostics): add passive message-end checks`.
- Один коммит должен содержать одну логическую единицу. Исследование, функциональность и правила агента разделять, если каждую часть можно проверить независимо.
- Перед коммитом проверить `git status`, diff и историю; не включать чужие или несвязанные изменения.
- После полного цикла изменения, проверок и устранения замечаний агент создаёт локальный коммит автоматически, если пользователь явно не запретил коммиты.
- Если работа состоит из нескольких независимых единиц, агент автоматически создаёт несколько Conventional Commits в порядке зависимостей.
- Коммит разрешён только после успешных релевантных проверок. При красной проверке или неясной принадлежности файлов остановиться без коммита и сообщить причину.
- После такого коммита автоматически выполнять `git push` текущей ветки в настроенный `origin`, если пользователь явно не запретил push и remote доступен.
- Если `origin` или upstream не настроен, создать локальный коммит и явно сообщить, что для первого push нужен адрес remote.
- Не публиковать релизы, не переписывать историю и не менять чужие удалённые ветки без отдельной явной команды пользователя.
