# Пассивное наблюдение за контекстным окном

## Задача и границы

Проверяем на обычной работе, появляются ли редакторские проблемы чаще в поздних ответах одного непрерывного участка контекста. Новых генераций, модельных судей и автоматических напоминаний нет. Текущие правила диагностики служат фильтром для просмотра, а не эталоном качества.

Наблюдение не требует искусственно удлинять сессии или выбирать дорогую модель. Сбор начинается после обычной загрузки обновлённого расширения. Уже сохранённым ответам метаданные задним числом не приписываются.

## Что записывается

`src/index.ts` принимает события Pi. `ContextObserver` в `src/runtime-diagnostics.ts` снимает метаданные в обработчике `context`, перед вызовом модели. `message_end` только копирует готовый снимок в существующую ограниченную очередь. Хэширование подсказки, обход истории, линтер и файловая запись в этот обработчик не добавлены.

В схеме `pi-russian-style-diagnostic/v2` сохранены прежние поля и добавлены:

| Поле | Смысл |
| --- | --- |
| `stop_reason` | Причина завершения; сравниваются только `stop`, без обрезанных `length` |
| `context.segment_id` | Случайный идентификатор непрерывного участка наблюдения |
| `segment_reason` | Начало наблюдения, успешное сжатие, переход по дереву или смена конфигурации |
| `observed_compactions` | Число успешных сжатий, замеченных после старта этого экземпляра расширения |
| `candidate_index` | Порядковый номер диагностического кандидата внутри участка, до постановки в очередь |
| `prompt_version` | SHA-256 встроенного русского блока, без его изменения |
| `pi_system_prompt_sha256` | SHA-256 строки `ctx.getSystemPrompt()` перед вызовом; при недоступном API — `null` |
| `thinking_level` | Доступный уровень рассуждения или `null` |
| `context_tokens` | Оценка Pi перед вызовом или `null` |
| `context_window` | Размер окна из оценки Pi или `null` |
| `context_percent` | Отношение известных токенов к размеру окна; иначе `null` |
| `usage_source` | `pi_context_estimate_before_call` либо `unavailable` |

Модель и провайдер берутся из самого ответа. Если они не совпадают с моделью снимка или снимок не был получен, весь `context` остаётся `null`. Исходные инструкции, содержимое окна и пути в новые поля не записываются.

`ctx.getContextUsage()` использует доступный учёт токенов и оценку последующих сообщений. Это не точный размер сериализованного запроса провайдеру. Хэш системной подсказки Pi не охватывает изменения сообщений другими расширениями и переписывание запроса в `before_provider_request`. Полная идентичность отправленного контекста не заявляется.

## Границы участков

Успешное `session_compact` всегда начинает новый участок; неудачная или отменённая попытка не считается сжатием. `session_tree`, смена модели, изменение хэша подсказки, уровня рассуждения или размера окна также разделяют наблюдения.

Перезапуск, `/reload`, возобновление и новая сессия начинают отдельный участок. Это сознательная потеря части возможных сравнений: без восстановления полного состояния безопаснее не склеивать наблюдения. `observation_start` не означает пустое окно. Ранний ответ может быть ранним только относительно момента подключения наблюдателя.

Очередь по-прежнему пропускает работу при перегрузке и отменяется при завершении сессии. Поэтому журнал не является полным учётом всех ответов. Пропуски внутри участка могут быть заметны по `candidate_index`; пропущенный хвост так восстановить нельзя. Короткие и нерусские ответы не проходят прежний диагностический фильтр.

## Разметка

Команды приведены в `README.md`, раздел «Наблюдение за длинными сессиями».

`--window-sample` создаёт файл один раз, с правами `0600` в новом каталоге `0700`. В нём остаются диагностические записи выбранных пар и наблюдения, подтверждающие их отбор. Полных ответов в нём нет. Для следующей независимой выборки укажи новый путь; не удаляй старую разметку ради обновления набора.

Правила отбора:

1. Только v2, `stop`, известные идентификаторы, хэш подсказки и конечные оценки заполнения от 0 до 100 процентов.
2. В участке не менее четырёх подходящих ответов; первый и последний разделены минимум 20 процентными пунктами заполнения.
3. Модель, провайдер, уровень рассуждения, версии правил и подсказки, размер окна и счётчик сжатий одинаковы. Участки с противоречащими дубликатами, повторяющимися индексами или уменьшением оценки заполнения пропускаются.
4. Одна пара на участок. Одна контрольная пара с `clean` включается при наличии; остальные выбираются по устойчивому хэшу, без ручных оценок. `--limit` ограничивает число ответов и округляется вниз до полных пар.
5. Порядок показа перемешан по хэшу. Метаданные доступны в свёрнутом разделе диагностики; это удобство, а не строгая слепая процедура. Сначала оцени язык, затем открывай диагностические сведения.

Тексты восстанавливаются из локальных сессионных JSONL с проверкой времени, entry ID, провайдера, модели и SHA-256. Недоступный текст не заменяется другим: сервер сообщает о неполной фиксированной выборке. Существующий интерфейс сохраняет общую оценку, полезность решения и выделенные фрагменты. Для сравнения достаточно общей оценки обоих ответов пары.

Файл выборки и разметка приватны: содержат служебные идентификаторы, а разметка — выделенные фрагменты. Храни их в `.runtime/`, не добавляй в Git. Используй разные пути для выборки, разметки и сводки.

## Как читать сводку

Сводка строится только из фиксированной выборки и разметки. Она не читает сессии, не запускает модели, линтер и повторную оценку правил. Метка учитывается только при совпадении SHA-256; незавершённые пары показываются отдельно и не попадают в сравнение.

Для каждой конфигурации показаны число пар и сессий, ранние и поздние оценки, число ухудшений и улучшений, медианы заполнения и расстояния между кандидатами. Отдельно показаны размеченные `clean` и плохие ответы среди них. В сводке нет текстов, session ID и entry ID.

Рост плохих оценок в поздних ответах — повод посмотреть сами задачи, а не доказательство влияния длины контекста. Задачи различаются по сложности, участки одной сессии зависимы, контрольная пара с `clean` влияет на состав. Из этих данных нельзя считать общую распространённость дефектов или эффект самого расширения.

Если сопоставимых пар нет, продолжаем обычную работу без дополнительных расходов. Если в нескольких сессиях повторяется одна конкретная проблема, отдельно решаем, нужна ли точечная правка. Отсутствие заметных проблем — основание оставить текущие правила без расширения, но не утверждать, что всё семейство моделей проверено.
