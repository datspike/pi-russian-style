# Интерактивный Humanizer в `pi-russian-style`

**Статус:** черновик; независимое техническое ревью Astra учтено

## Зачем

`humanizer-ru` уже хорошо задаёт редакторский контракт, но для правки последнего ответа агент вынужден временно записывать текст, линтить его, исправлять и повторно выводить в чат. Это медленно, дублирует большой текст в output и не оставляет явной связи между источником и отредактированной версией.

Новый контур должен сделать редактуру явным действием внутри существующего `pi-russian-style`, не создавая отдельный package и не превращая постоянный русский стиль в агрессивный автокорректор.

## Границы

Входит:

- явная интерактивная редактура последнего содержательного assistant-сообщения через `/ru-clean`;
- детерминированный source snapshot, draft, lint и публикация производного ответа;
- ленивое раскрытие Humanizer tools только на время активной редакторской сессии;
- помощь при правке файлов, docstring и комментариев без требования вручную указывать range;
- единая поставка extension, skill, prompt и lint в `pi-russian-style`.

Не входит:

- автоматическая правка обычных ответов по результату фоновой диагностики;
- новый универсальный редактор исходного кода, дублирующий `read`, `ast-index-nav` и `edit`;
- перестройка файлов или кода вне явно выбранных моделью текстовых фрагментов;
- оптимизация текста до нулевого числа `WARN`.

## Пользовательские сценарии

### `/ru-clean`

1. Пользователь вызывает `/ru-clean` без цели.
2. Extension проходит активную ветку через `ctx.sessionManager.getBranch()` и выбирает завершённое assistant-сообщение с непустым текстом, исключая tool results и помеченные публикации Humanizer. Обычный assistant-recap без метки не считается надёжно отличимым и требует отдельной явной политики.
3. Extension сохраняет `entryId`, хеш, версию редакторского контракта и неизменяемый source snapshot, затем сам создаёт первую ревизию draft.
4. Модель получает snapshot и редакторский контракт с явным указанием, что draft уже существует: она не вызывает `humanizer_create_draft`, а применяет точечные правки и запускает lint.
5. `humanizer_publish` переводит конкретную ревизию в состояние `publish_pending`; extension публикует её только после корректного служебного финала. Любой другой терминальный assistant-финал отменяет pending publication. Исходное сообщение не меняется.

Итоговое сообщение содержит короткую provenance-квитанцию: источник и число `ERROR`/`WARN`. Сводка структурного diff доступна отдельной сворачиваемой session entry; нельзя автоматически заявлять о сохранении композиции, пока это не доказано отдельной проверкой.

### Явная цель

Если пользователь передал `/ru-clean <запрос>`, extension активирует Humanizer tools и пересылает запрос как `/skill:humanizer-ru <запрос>` с раскрытием skill. Запись `<запрос> /ru-clean` в конце обычного сообщения преобразуется в тот же skill-запрос через обработчик `input`. Этот путь не создаёт chat-draft и не подменяет прошлое assistant-сообщение. Если цель — файл, документ, фрагмент или комментарий, модель находит область обычными инструментами и применяет результат через обычный `edit`.

### Файлы, docstring и комментарии

`/skill:humanizer-ru` остаётся естественным интерфейсом. Модель сама находит область по запросу и минимальному коду вокруг неё. Extension при необходимости хранит набор текстовых замен как draft, линтит только их и помогает применить точные patch-операции. Он не требует от пользователя диапазон строк и не принимает архитектурные решения за модель.

## Текстовый prompt

`prompts/ru-clean.md` остаётся обычным редактируемым Markdown-файлом с frontmatter и текстом инструкции. Но после перехода он не должен загружаться Pi как стандартный prompt template.

Команда `/ru-clean` без аргументов читает этот файл как свой instruction resource, подставляет точный source snapshot и запускает редакторский ход. Так файл по-прежнему легко править руками, а extension получает контроль над выбором источника и жизненным циклом draft. Ветка с аргументом передаётся в skill через `sendUserMessage()`.

## Инструменты и контекст

Pi позволяет зарегистрировать custom tools и включать их через `pi.setActiveTools()` во время сессии. Humanizer tools должны быть зарегистрированы пакетом, но отсутствовать в активном наборе по умолчанию.

При явном `/ru-clean` или `/skill:humanizer-ru` extension:

1. добавляет только Humanizer tools к текущему active tool set;
2. запускает редакторский ход;
3. по публикации, отмене или ошибке удаляет только свои tools из текущего набора, не восстанавливая старый список целиком и не затирая инструменты других extensions.

`input` получает необработанный текст до раскрытия skill, поэтому явный `/skill:humanizer-ru` можно надёжно распознать и раскрыть tools до agent turn. Аргумент зарегистрированной команды `/ru-clean` — такой же явный сигнал: extension пересылает его через `sendUserMessage()` с `expandPromptTemplates: true`; во время активного хода он ставится в очередь `followUp`. Для явного суффикса ` /ru-clean` в конце интерактивного или RPC-сообщения extension возвращает input-transform в `/skill:humanizer-ru <запрос>`. Произвольный естественный запрос без команды продолжает работать текущим skill-workflow без staging tools; не надо добавлять глобальный gateway tool только ради эвристики.

## Черновик и публикация

Draft хранится в extension state и сохраняется в session custom entry как аудитный журнал, а не записывается в рабочий проект как временный Markdown-файл. После `/reload` draft не восстанавливается: пользователь запускает новый явный workflow.

Минимальный набор инструментов:

- initial draft для `/ru-clean` создаёт extension из source snapshot; отдельный model-call для копирования не нужен;
- `humanizer_create_draft` создаёт draft только для явного файла, docstring, comment или фрагмента;
- `humanizer_patch_draft` — заменить один точный фрагмент в `expectedRevision`;
- `humanizer_patch_draft_set` — атомарно применить несколько непересекающихся точных замен в `expectedRevision`; по умолчанию линтит новую revision, а `lintAfter: false` оставляет его для промежуточной правки; при ошибке ни одна правка не вносится;
- `humanizer_lint` — проверить текущий draft;
- `humanizer_inspect` — вернуть краткую структуру, lint и diff summary;
- `humanizer_publish` — пометить draft готовым к публикации;
- `humanizer_discard` — отменить активную редактуру.

После `humanizer_publish` обработчик `message_end` заменяет только финальный assistant-ответ с допустимым `stopReason` и точным служебным маркером на сохранённый draft. Любой другой терминальный assistant-финал отменяет pending publication и очищает job. Это сохраняет исходный ответ и не даёт старому draft заменить поздний ответ.

Обычный `message_end` для пассивной диагностики остаётся неизменяемым: он никогда не исправляет и не заменяет ответ. Служебный финал должен быть коротким, потому что `message_end` срабатывает после стриминга и его могут увидеть TUI или RPC-клиенты до replacement.

## Архитектура поставки

```text
pi-russian-style/
├── src/
│   ├── index.ts
│   ├── prompt.ts
│   ├── diagnostics.ts
│   ├── runtime-diagnostics.ts
│   └── humanizer.ts
├── skills/humanizer-ru/
├── prompts/ru-clean.md
└── tests/
```

`pi-russian-style` становится канонической runtime-поставкой `humanizer-ru`: skill, references, corrections и lint версионируются вместе с extension. В vault остаётся видимое зеркало или тонкий wrapper, но не вторая вручную поддерживаемая копия.

## Совместимость с текущей диагностикой

Независимое ревью подтвердило два конкретных долга текущего контура:

- `runHumanizer()` передаёт lint excerpts в `humanizer.findings`, а `createDiagnosticWorker()` сохраняет их в диагностический JSONL. Это нарушает обещание не хранить исходный текст ответа; в пассивную запись должны попасть только разрешённые метаданные без `excerpt` и произвольного `output`.
- Интеграционный тест, ожидающий `verdict: review` для текста с длинным тире, устарел после перевода таких признаков в контекстные `WARN`. Он должен проверять транспортный контракт lint и отдельно различать `ERROR` и информационные `WARN`.

Текущая пассивная диагностика использует признаки, часть которых появилась до нового редакторского контракта: process opening, архитектурные метафоры и отдельные английские рабочие термины. Её нельзя превращать в quality gate нового Humanizer. Сейчас `notify` зависит от сильного `style_debt_english`, а не напрямую от `humanizer.verdict`; это нужно сохранить как мягкое предложение вызвать `/ru-clean`, а не оценку качества текста.

## Минимальная последовательность работ

1. Закрыть два долга пассивной диагностики: исключить excerpts из JSONL и обновить устаревший lint-тест.
2. Провести технический spike публикации на поддерживаемой версии Pi: replacement → TUI/RPC → JSONL → reload → следующий контекст.
3. Реализовать только chat-сценарий `/ru-clean`: source snapshot, draft, lint, `publish_pending` и provenance.
4. Добавить тесты на отмену pending publication, конкурирующий запуск, сохранение исходного сообщения и очистку active tools. Reload не восстанавливает draft.
5. Перенести skill и lint в canonical package layout после подтверждения chat-сценария.
6. Отдельно добавить staging для файлов и комментариев, только если chat-сценарий подтвердит ценность механизма.

## Критерии готовности первого среза

- `/ru-clean` выбирает точный source entry, а не «прошлый текст по памяти модели».
- Исходное assistant-сообщение неизменно.
- Итог публикуется отдельным assistant-сообщением без второго полного вывода от модели.
- Humanizer tools отсутствуют в обычных ходах и видны только во время активного job.
- `ERROR` и недоступный lint блокируют публикацию; одиночный `WARN` остаётся контекстным сигналом.
- При отмене или ошибочном терминальном assistant-финале pending publication отменяется; после `/reload` draft не восстанавливается. Humanizer убирает только свои tools из текущего active set.
- Повторный `publish` не создаёт дубликат, а устаревший или неоднозначный patch ничего не меняет.
- Пассивная диагностика по-прежнему не блокирует TUI, не меняет обычные ответы и не сохраняет фрагменты исходного текста.
